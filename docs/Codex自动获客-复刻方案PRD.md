## 一、核心结论（决策摘要）

| # | 结论 | 依据 |
|---|---|---|
| 1 | **先做给自己用**：MVP 验证"改写内容→真实转化成交"，不急着商品化 | AI 亦仁 + 乔川/大周案例一致 |
| 2 | **定位转向"辅助创作"**：不做"克隆/搬运"话术，做"理解爆款结构→生成原创内容"的正向定位 | AI 亦仁合规警告（采集=爬虫、改写=擦边） |
| 3 | **先用在珠宝店场景**：垂直切口 = 珠宝/鉴藏品类小红书获客，天然验证场 | 用户独有资产，别人抄不走 |
| 4 | **技术底座全部开源可抄**：小红书采集/发布/MCP 均有成熟开源组件 | Step3 GitHub 调研 |
| 5 | **风控是核心工程问题**：IP 隔离、单号单 IP、养号、发布节奏、克隆比例 | 玫瑰克隆披露 + 乔川踩坑 |
| 6 | **视频只是钩子**：完整销售工作流 = 采集→内容→发布→引流（直播间/私域）→成交，工具只解决前 4 步中的内容生产部分 | 用户判断 + 亦仁"赚流量的钱" |

## 二、产品定义

### 2.1 一句话定义
**输入行业关键词 → 自动采集小红书对标笔记 → 评分筛选可模仿对象 → AI 辅助创作（标题/正文/标签/图片）→ 发布到自有账号 → 引流直播间/私域成交**。

### 2.2 目标用户（第一阶段只有一个人：自己）
- 行业：珠宝/鉴藏（翡翠、宝石、手串等），后续可扩展到襄阳市本地生活商家
- 场景：小红书账号运营 → 内容引流 → 直播间/到店成交
- 核心诉求：把"找对标→写内容→发笔记"从 2 小时/篇降到 5-10 分钟/篇，稳定日产

### 2.3 边界（不做）
- 不做矩阵号规模发布（第一阶段 1-3 个账号）
- 不做直播间本身（只做内容引流侧）
- 不做"搬运克隆"（合规风险，定位辅助创作）

| 模块 | 功能 | 规格 |
|---|---|---|

## 四、评分设计（待验证）

> 画面只有"评分"字样，无权重细节；以下为惯例指标设计（Step3 已验证小红书的互动指标生态）

```
评分 = 内容质量分(结构化/可模仿性) × 数据热度分(低粉高赞优先) × 时效分(近期发布优先)
```
- **数据热度**：点赞/收藏/评论/转发，重点看**低粉高赞**（小号爆款=可复制性强，MediaClaw 已验证此玩法）
- **内容可模仿性**：结构清晰度（痛点→方法→产品/案例）、标题公式可提取、图片可复用度
- **匹配度**：与目标关键词/行业相关性

## 五、技术架构（可抄方案）

### 5.1 整体形态
**本地部署 Web 应用**（对标视频工具 127.0.0.1:8791）+ 浏览器自动化/逆向 API 采集 + 大模型 API 生成。

### 5.2 组件选型（Step3 开源清单，均已验证存在）
| 层 | 候选 | 说明 |
|---|---|---|
| 采集层 | **xiaohongshu-mcp**(Go) / **rednote-mcp**(Node) | MCP server，搜索/浏览/发布，Claude/Codex 可直接调 ⭐ 与视频工具同思路 |
| 采集层备选 | XHS-Downloader / redbooks / xiaohongshu-cli / Spider_XHS | Python 生态，链接提取/作品采集/无水印下载 |
| 自动化层 | Playwright / BrowserAct（反检测） | 登录态操作、DOM 级交互；多账号用指纹浏览器隔离 |
| 环境隔离 | 比特浏览器 / 指纹浏览器 + 住宅 IP | 每账号独立指纹+IP，防关联 |
| AI 生成层 | **Codex CLI（ChatGPT 订阅，首选）** / 火山方舟（豆包 API）/ OpenAI API / DeepSeek API | 见 §5.5 多后端设计 |
| Web 框架 | Python FastAPI/Flask 或 Node | 本地服务 + 前端界面 |
| 数据存储 | SQLite（本地）/ 飞书多维表格 | 对标池、内容库、发布记录 |

### 5.5 模型/内容生成设计（v1.3 修订：MVP 用"人+订阅"，API 留作后续）

> 用户拍板（2026-10-25）：模型先做简单的、用现成的——用已付费的豆包订阅；程序不强制接 API。内容生成**先直接抄原笔记图文进编辑界面（与视频一致），用户人工调整或用豆包生成新图新文**；API 自动化留作后续优化。
> 事实核查：豆包**订阅**=客户端功能额度（聊天/生图等高级功能共享池），**不能被脚本/API 直接调用**；豆包模型的 API 出口是火山方舟（按量付费）；Codex CLI 可用 ChatGPT 订阅 `codex exec` 非交互调用（订阅配额内不按 token 计费）。

**MVP 内容生成链路（v1.3，不依赖任何模型 API）**：
```
采集 → 评分 → 选择作品 → 编辑界面自动带出原笔记图文（标题/正文/标签/图片）
      → 用户人工调整 / 替换图片 / 用豆包订阅（人工）生成新图新文 → 发布
```
- 程序只做"搬运 + 编辑框架"，不做自动改写（与视频 24s/28s 帧一致：带出原作品、可删改调序）
- 编辑界面保留：标题(≤50字)/正文(≤1000字)/标签(空格分隔)/图片(可删改调序追加)/可见范围/发布账号
- 后续优化（Phase 2，做成配置项）：接 API 自动生成——`MODEL_BACKEND=volc|codex_cli|openai|deepseek`，统一生成函数接口

**后续 API 自动化后端候选（暂不实现，记录在案）**：
| 后端 | 计费 | 调用方式 | 备注 |
|---|---|---|---|
| 火山方舟 API（豆包同源模型） | 按 token（便宜） | OpenAI 兼容 API `ark.cn-beijing.volces.com` | 与"用豆包"偏好一致，推荐首选 |
| Codex CLI | ChatGPT 订阅 | `codex exec` 非交互 | 0 额外成本，与视频工具同源 |
| OpenAI / DeepSeek API | 按 token | OpenAI 兼容 | 备选 |

### 5.3 参考实现（生财已读帖）
- **乔川路径1**：飞书多维表格(脚手架) + Augment 插件(微调/发布/降重) + Playwright + 比特浏览器多账号
- **乔川路径2**：OpenClaw(大脑) + 比特浏览器(操作) + 飞书(仓库/推送)，4 监听模块，3 天交付 5 位数
- **大周路径**：手机版 App（链接→一键改写→发布），"按钮能少则少"

### 5.4 技术风险
- 小红书接口逆向存在失效风险（平台改版）→ 备选走 DOM 自动化
- 采集频率触发风控 → 请求间隔控制 + 量走接口
- 大模型调用成本 → 选 DeepSeek/中转，标题正文量控制

## 七、风控与合规设计（工程必做）

### 7.1 平台风控（小红书实测情报，Step3）
| 风险 | 对策 |
|---|---|
| 多模态指纹检测（2025Q4 起，改滤镜无效） | 图片不直接复用他人原图；自拍/自有产品图 + 设计元素重做；混剪比例 <50% |
| IP 关联/污染 | 单号单 IP（住宅 IP），指纹浏览器隔离，禁止裸 IP 采集 |
| 高频操作风控 | 请求间隔 1000ms+；发布间隔随机化；单日发布量上限 |
| 新号限流 | 新号 0-3 天不发布，先浏览/点赞养号进池 |
| 引流扣分 | 微信外链被举报触发"交易导流"：先引小号/粉丝群再转化 |

### 7.1b 引流合规（深挖补充 2026-10-25，官方规则已查证）
- **小红书官方"私信获客工具"已成为交换联系方式的唯一指定路径**（2025-01-07 生效，生财帖已查证），私信内发微信号/手机号将禁言
- 开通条件：近30天聚光/乘风投流消耗>0 的商家（2025-04-16 起）
- 聚光平台 2025-12 迁移乘风，投流入口变化
- **结论**：我们工具聚焦"内容生产→发布→获赞评论"，**引流环节交由用户走官方获客工具**（需用户店铺有投流消耗），不碰第三方截流/私信群发（平台打压区）

### 7.2 合规（AI 亦仁红线 + 工具方披露）
- **业务逻辑不建立在采集+搬运版权内容上**：采集仅作"理解爆款结构"的研究用途；发布内容以原创/自有素材为主
- 话术从"克隆/伪原创"改为"辅助创作/爆款结构学习"
- 版权：不使用他人原创图片/出镜人像；模型生成图注意平台规范
