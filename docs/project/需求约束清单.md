### 3.2 架构与登录方案演进（2026-10-26~28，关键）

| # | 决策 | 内容 |
|---|---|---|
| D8 | **移除 Docker** | 不再使用 xhs-mcp 容器（采集/发布）；开发与生产统一为外部 Chrome 驱动，避免"内外两套环境不一致难调试" |
| D9 | **采集/发布载体 = 外部 Chrome + CDP** | 独立 profile `~/.codex-xhs-profile` + 端口 9223；CDP 连接复用登录态（Chrome 144+ 运行时远程调试） |
| D10 | **生产形态无豆包/无 CDP 辅助** | 交付给普通客户时没有 AI 环境，CDP 只用于调试；生产靠内置引导脚本（`app/scripts/setup_chrome.py` 带参数启动 Chrome + 打开 chrome://inspect 配置页；`pick_chrome.py` 文件对话框选 Chrome）引导用户自助开启远程调试 |
| D11 | **Cookie 失效闭环（生产主路径）** | APP 检测失效 → 提示 → 用户点链接打开小红书首页扫码 → 回 APP 点「立即读取 Chrome 登录态」（读 .codex-xhs-profile 的 Cookie 库）→ 成功即生效；手动导入 Cookie 文本为备选（无效拒绝） |
| D12 | **跨窗口自动导入不承诺** | 生产无 CDP 时不能跨窗口监控扫码完成并自动导入 Cookie；引导用户手动点按钮是主路径（不在此上做自动化承诺） |
| D13 | **发布永远手动（红线）** | `/api/publish` 只由用户在前端手动触发；任何自动化环节不得代发（平台 2026-03 公告点名 AI 托管发布） |
| D14 | **一切从前端驱动** | 用户操作走前端按钮；后端不主动拉起浏览器/弹窗（登录弹窗由 APP 前端触发） |
| D15 | **唯一 Chrome 单窗口单 Dock 图标** | CDP 全程一个 Chrome 窗口一个图标；发现多窗口/多图标先清理再继续；CDP 前后清理无关 tab（绝不关闭 APP 窗口） |
| D16 | **路径可移植** | 代码/文档一律 `~`/`$HOME`/`os.path.expanduser`，不写死 /Users/<用户名>（换机/换系统直接跑） |
| D17 | **MCP 是调试期辅助** | MCP/远程接口是多一层跨进程调试负担，最终可拆；但拆时须注意生产无 AI 环境，不依赖 MCP 能力 |
| D18 | **前端技术栈** | Vue3 + Vite + TypeScript（用户拍板）；npm run build → app/web |

### 3.3 产品功能决策（2026-10-26~28）

| # | 决策 | 内容 |
|---|---|---|
| D19 | 界面 4-Tab | 采集 → 评分 → 克隆 → 草稿/发布（顶部流程条，非左侧竖排） |
| D20 | 搜博主列表功能去掉 | 按关键词搜索并采集用户（博主列表）不做；「采集客户」（笔记互动用户）保留 |
| D21 | 评分引擎权重 | like_fan_ratio 40% / low_fan 25% / interaction_health 20% / freshness 15%；卡片右上角分数由四维加权而来 |
| D22 | 采集数据用完即失效 | 每次搜索 DELETE FROM notes（不长期存库）；长期留存仅"发布/存草稿"的笔记 |
| D23 | 采集数量语义 | 用户给目标数量（如 50），采集到满足即停；中途可停止，停止后可排序 |
| D24 | 采集筛选条件 | 支持小红书搜索筛选（类型/时间等）透传；采集开始页可配筛选条件 |
| D25 | 克隆图片规则 | 主图结构分析后按封面优先/去重提取；发布图片可放大查看、追加新图、拖拽排序 |
| D26 | 草稿可再编辑再发布 | 保存草稿后用户可查看、继续编辑、再发布 |
| D27 | 互动数据/用户采集调研 | 已做调研（有人做，对甲方价值=找可模仿的高价值低粉作者）；是否并采/分采及设计待定稿（服务于"找高价值可参考笔记模仿"总目标） |
| D28 | 养号功能 | 自动浏览开放、点赞/评论/收藏谨慎档（只在测试号启用）；账号买卖不做（法律风险） |

## 五、讨论过程中被纠正/澄清的认知（重要，避免重犯）

| # | 认知 | 澄清 |
|---|---|---|
| 1 | "视频是完整课" | ❌ 视频只是推广/宣传/引流钩子，不是完整课程 |
| 2 | "复刻成自己用" vs "做成产品卖给同行"是一件事 | ❌ 两阶段：先自己做 MVP 跑通验证，再决定产品化 |
| 3 | "克隆"是核心价值 | ⚠️ 建议"辅助创作"正向定位（采集=爬虫、改写他人内容=擦边） |
| 4 | 调研方法可能只有一种 | ❌ 多个入口多通道尝试判断 |
| 5 | 工具只解决内容生产 | ⚠️ 完整销售工作流=内容→发布→引流→成交，工具只覆盖内容生产部分 |
| 6 | 用订阅模型做不了自动化 | ❌ Codex CLI 订阅可非交互调用；豆包订阅不含 API token 但方舟 API 可按量付费 |
| 7 | 生产环境也能用 CDP 全自动 | ❌ 开启 CDP 对用户麻烦且有安全风险；生产必须引导用户自助（扫码+读 Cookie 为主路径） |
| 8 | 跨窗口/跨域名能自动导入 Cookie | ❌ 本机 APP 不能读另一域名的 Cookie；必须用户回 APP 点按钮 |
| 9 | 采集=一个接口调用 | ⚠️ 采集是"多次搜索+详情补全+评分"的完整过程；按目标数量采集到满足即停 |

## 六、用户长期偏好（跨任务，来自 profile + 本次）

- 纯文字/表格化/普通 MD/PDF 交付；社交文案严禁 AI 化生硬表述
- 技术栈限定 TypeScript/Go/Rust/Python（排除 Java/Clojure）
- 消费观务实（高性价比优先）；偏好省力工具
- 自主推进默认"继续/不用问我"，但关键节点设人工闸口
- 涉及飞书知识库归档先询问
- 执行力风格：能 UI 自动化部分尽量自动化完成；测试分步进行、每测一点汇报
