# 项目开发对齐机制（Phase Gate SOP）v1.0

> 用户确认：实施前需对齐，每阶段开始前有会议，会议后对齐再进行正式开发，开发中不断迭代。
> 适用：codex-xhs-autogain 项目所有后续阶段。

---

## 一、为什么要会议（对齐的价值）

- 避免"埋头开发方向跑偏"——每个阶段开始前对齐目标、范围、验收标准
- 开发中发现问题随时迭代，不必等阶段结束
- 让用户参与关键决策（行业词、账号、模型、合规），不重复沟通

## 二、阶段门（Phase Gate）流程

```
┌─────────────────────────────────────────────────────┐
│  ① 阶段启动会议（Gate）                              │
│     目标 / 范围 / 验收标准 / 资源准备 / 风险预判      │
│     → 用户确认（✅/❌）                               │
├─────────────────────────────────────────────────────┤
│  ② 正式开发（迭代循环）                              │
│     小步开发 → 自检 → 汇报进展 → 用户反馈 → 修订      │
│     （每个里程碑可交付可验收）                        │
├─────────────────────────────────────────────────────┤
│  ③ 阶段交付 + 复盘                                   │
│     交付物清单 / 验收结果 / 经验教训                  │
│     → 决定下一阶段（继续/调整/终止）                  │
└─────────────────────────────────────────────────────┘
```

## 三、阶段会议议程模板（每次会议固定 5 项）

| # | 议程 | 产出 |
|---|---|---|
| 1 | **目标对齐**：本阶段要达成什么（一句话+可量化指标） | 目标描述 |
| 2 | **范围确认**：做什么/不做什么（明确边界） | 范围清单 |
| 3 | **验收标准**：做完怎么算通过（可验证清单） | 验收清单 |
| 4 | **资源准备**：需要哪些账号/工具/key/环境（谁准备、何时就绪） | 资源清单 |
| 5 | **风险与假设**：已知风险、需要验证的假设 | 风险登记 |

**会议形式**：我（Agent）会先产出《阶段启动文档》（含上述 5 项的方案），交付给你审阅；你确认或提出修改后，我才进入开发。会议文档归档到仓库 `docs/project/gates/`。

## 四、MVP 阶段门规划（对照 PRD §八）

| 阶段门 | 名称 | 会议触发点 | 开发内容 |
|---|---|---|---|
| G1 | W1 地基 | 现在（首次会议） | 环境搭建 + 采集组件跑通 |
| G2 | W2 创作 | W1 验收通过后 | 评分 + AI 辅助创作链路 |
| G3 | W3 发布 | W2 验收通过后 | 发布模块 + 账号绑定 |
| G4 | W4 验证 | W3 验收通过后 | 真实发布 + 数据复盘 |

## 五、迭代规则（开发中）

1. **小步交付**：每完成一个可运行功能即汇报（不是憋到阶段结束）
2. **用户反馈优先**：用户提出的修改直接进下一迭代，不搁置
3. **自检纪律**：每次交付前验证（运行测试/回读产物），不交付未验证内容
4. **变更记录**：PRD/文档每次修订记版本号+变更说明（v1.0→v1.1…）
5. **不重复沟通**：已确认决策写入 PRD「〇、已确认决策」表，新对话/新阶段直接引用
