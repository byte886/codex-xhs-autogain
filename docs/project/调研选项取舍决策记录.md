## 决策点 1：整体实现路径（4 条候选路）

调研中出现了 4 条完全不同的实现路线：

| 候选 | 来源 | 形态 |
|---|---|---|
| **A. 本地 Web 复刻**（视频同款） | 视频本身（127.0.0.1:8791） | 本地部署 Web 应用：关键词→采集→评分→生成→发布 |
| **B. 飞书多维表格 + Augment 插件**（乔川路 1） | 生财帖 55188128214188214 | 飞书表格做脚手架 + AI 插件生成 + Playwright 发布，定制服务 1w/单 |
| **C. OpenClaw + 比特浏览器 + 飞书**（乔川路 2） | 生财帖 14588155124111142 | 开源 AI 智能体（大脑）+ 指纹浏览器（手）+ 飞书（数据仓库），3 天交付 5 位数 |
| **D. 手机 App**（大周路） | 生财帖 14588582154552442 | 手机版"链接→一键改写→发布"，月卡 100+ 付费用户收 3w |

**✅ 选择 A（本地 Web）**，理由：
1. **与目标一致**：我们的目标是"抄他的工具"，A 就是视频里工具的原型，功能边界已被画面证实（采集面板/克隆界面/发布账号全部是 Web UI）
2. **可扩展性**：A 的"服务 + 界面"结构最容易被后续加模块（定时/多账号/数据回流）
3. **跨平台**：本地 Web 服务 macOS/Windows 都能跑（视频是 Windows，你本机 macOS，本地服务天然跨）
4. B/C 是把数据仓库建在飞书——绑定第三方，且乔川做的是"给别人交付"，不是"给自己用"
5. D 手机版把能力压得很窄（链接粘贴→改写→发布），无法承载"关键词采集→评分→选品"的完整闭环，且你的核心场景是**珠宝店内容工厂**而非轻量单发

**排除 B/C/D 的深层理由**：
- B/C 的核心价值（多账号并发、客户交付）对你第一阶段（1-3 个号自己用）用不上
- D 月卡模式验证了"简单到不用学"的产品哲学（值得借鉴 UI 极简），但功能上限不满足采集+评分需求
- **回退方案**：若 A 开发中遇到采集困难，可退回 C 的"OpenClaw 驱动浏览器"思路（它们的采集层可复用）

## 决策点 3：自动化/发布层（5 个候选）

| 候选 | 调研发现 | 状态 |
|---|---|---|
| **Playwright** | 乔川路 1 用其并发控制比特浏览器多账号发布；标准工业方案 | ✅ 选择（配合采集组件） |
| **BrowserAct** | 掘金实测：反检测浏览器自动化 CLI，stealth-extract 直接拿小红书首页内容；专为 AI Agent 打造 | 🔶 关注（若 Playwright 被封再用） |
| **比特浏览器** | 乔川两帖都用：独立纯净网络+指纹环境防风控；本地接口+窗口 ID | 🔶 W3 多账号时引入 |
| **八爪鱼 RPA** | 应用市场有"小红书文案一键克隆发布"（AI 改写开关） | ⚪ 排除：RPA 流程易被平台改版击穿（乔川原话"平台改版就废"），且不透明 |
| **油猴脚本** | mcxiaoxiao 方案依赖 | ⚪ 排除：浏览器依赖、稳定性差 |

**✅ 选择 Playwright + （W3 加）比特浏览器**：
- Playwright 是工业标准，可控粒度（等待/重试/指纹注入），乔川验证过可行
- 比特浏览器只在多账号（W3）引入——W1 单账号用 Playwright 直接驱动本机浏览器即可，先简单
- BrowserAct 记入备选：它解决"反检测"正是 Playwright 的软肋，若 W1 实测 Playwright 触发风控就切换
- 排除八爪鱼：乔川明确踩过坑（RPA 流程平台改版即废）

## 决策点 4：模型后端（4 个候选）

| 候选 | 计费 | 调研发现 | 状态 |
|---|---|---|---|
| **Codex CLI（ChatGPT 订阅）** | 订阅内（Plus $20/月） | OpenAI 官方：Codex 含于 ChatGPT 各套餐，CLI 登录即可，`codex exec` 非交互模式；**视频工具同名同源** | ✅ 首选 |
| **火山方舟（豆包 API）** | 按 token | 豆包订阅=客户端功能额度**不含 API**；方舟 API 按量付费 | 🔶 备选 |
| **OpenAI API** | 按 token | 质量稳但贵 | 🔶 备选 |
| **DeepSeek API** | 按 token（便宜） | 成本敏感批量 | 🔶 备选 |

**✅ 首选 Codex CLI**：
1. **0 额外成本**：用户已有订阅，订阅配额内不按 token 计费
2. **同源**：视频工具名字就是 Codex——生成逻辑用同一引擎，最接近原版效果
3. `codex exec` 已确认支持非交互/自动化调用（事实核查于 2026-10-25）

**排除理由**：
- 豆包订阅被排除**作为后端**（不是排除豆包）：会员额度不能用于脚本 API 调用；但方舟 API 保留为备选
- OpenAI/DeepSeek API 非必要不先接：要买 key、按量计费
- **设计**：统一抽象层 `MODEL_BACKEND=codex_cli|volc|openai|deepseek` 配置切换，首版只实现 codex_cli，需要时加

## 决策点 5：数据存储（2 个候选）

- 飞书保留为 W2 的"数据回流展示"可选增强，不阻塞

## 决策点 6：竞品形态定位（为什么不做成玫瑰克隆/社媒虾那样）

调研发现的成熟竞品：
| 竞品 | 形态 | 价格 | 为什么不做成那样 |
|---|---|---|---|
| MediaClaw 社媒虾 | Codex+MCP 浏览器扩展+会员积分 | 积分制 | 是"给 Codex 的数据接口"，非完整获客工具；我们自建闭环更直接 |
| 玫瑰克隆 | 27 功能伪原创全套 | 45/98/168 买断 | 功能太多（视频/换脸/海报等），MVP 只做核心链路；且"伪原创"话术正是合规风险点 |
| 红薯侠/红薯通AI/AnyToCopy | 链接复刻/关键词生成 | - | 单点工具，无采集→评分→发布闭环 |
| 乔川/大周 | 定制服务/月卡产品 | 1w 单 / 月卡 | 商业模式参考，技术已吸收进决策点 1 |

**✅ 定位：不做通吃工具，做"珠宝/翡翠垂直 + 辅助创作"闭环**（依据：AI 亦仁"垂直人群不做通吃工具"、大周"通杀=红海无壁垒"）

| **低粉高赞优先** | MediaClaw 官方玩法：给 Codex 的数据分析里专门有"Find low-follower, high-like accounts"场景 | ✅ 采用 |
