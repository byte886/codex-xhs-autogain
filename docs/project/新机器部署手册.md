# 新环境开发环境部署手册（Mac 交接用）v1.1

> 目的：在另一台 Mac 上把 codex-xhs 系统作为**开发环境**跑起来（Docker 采集/发布容器 + Python 业务壳 + 前端），满足**新环境调试**（开发联调）与**演示**（跑通全链路）两类需求。
> 生成：2026-10-26（本机→新机交接）；适用于 macOS。本机特有/敏感内容一律不进仓库，需在新机重新生成（见 §6）。
>
> **定位声明（重要）**：本手册是**开发环境部署**，不是生产部署。因此：
> - 不追求稳定性/7×24/多账号并发，数据可随时丢弃重建（测试数据随便造）
> - 目标是"能改代码、能调试、能演示"，一切以方便开发联调为准
> - 生产化（多账号矩阵、稳定性、监控、权限）不在本手册范围，属后续产品化阶段再议

---

## 0. 系统全景（先建立心智模型）

```
┌─ 浏览器（日常 Chrome）────────────┐
│ 小红书新号登录态（外部浏览器）     │
└───────────┬────────────────────┘
            │ ① CDP 导出 cookies.json（mac-system-toolkit 技能）
            ▼
┌─ Docker 容器「xhs-mcp」:18060 ────┐  ← docker compose up
│ xpzouying/xiaohongshu-mcp         │  小红书 MCP 后端：搜索/详情/发布
│ cookies.json 注入（登录态）        │
└───────────┬────────────────────┘
            │ ② MCP HTTP (localhost:18060/mcp)
            ▼
┌─ Python 业务壳 :8791 ─────────────┐  ← uvicorn server:app
│ FastAPI：采集流水线/评分/一键克隆/ │  前端 http://127.0.0.1:8791
│ 发布（拟人化护栏+熔断）/SQLite     │
└─────────────────────────────────┘
```

## 1. 前置依赖

| 依赖 | 版本要求 | 说明 |
|---|---|---|
| Git | 任意 | 克隆仓库（SSH 走 443，被墙时 https 需代理/VPN） |
| Docker Desktop | 当前稳定版 | 起 xhs-mcp 容器；macOS 需安装并启动 |
| Python | **3.11-3.13** | 3.14 有已知坑（部分库编译失败），不要用 |
| pip | 跟随 Python | 装业务壳依赖 |
| 技能（豆包内） | mac-system-toolkit | CDP 导出 cookie 的脚本在技能目录，不在仓库 |

## 2. 克隆与定位

```bash
# 建议放桌面，与仓库内路径假设一致（server.py 用 parents[3] 定位仓库根，放哪都行但保持结构）
git clone git@github.com:byte886/codex-xhs-autogain.git ~/Desktop/codex-zhuke
cd ~/Desktop/codex-zhuke
# 确认目录：app/ docker/ docs/ data/ 需存在（data/ 初始可能为空目录）
```

## 3. 起 Docker 容器（采集/发布 MCP 后端）

```bash
cd ~/Desktop/codex-zhuke/docker
docker compose up -d          # 拉 xpzouying/xiaohongshu-mcp:latest
docker logs xhs-mcp           # 确认无报错
curl -s http://localhost:18060/mcp -o /dev/null -w "%{http_code}\n"   # 期望 4xx（HTTP MCP 端点响应）
```

- 端口：`18060`（写死在 docker-compose.yml 与 server.py MCP_URL）
- 数据卷：`./data`（cookies.json、config、home）、`./images`（采集图片）

## 4. Python 业务壳（FastAPI :8791）

```bash
cd ~/Desktop/codex-zhuke/app
python3 -m venv .venv && source .venv/bin/activate
pip install fastapi "uvicorn[standard]" pydantic   # 依赖很轻，仅此三件 + 标准库
# 启动（必须指定 --app-dir）
python3 -m uvicorn codex_xhs.server:app --host 127.0.0.1 --port 8791 --app-dir app/src &
# 验证
curl -s http://127.0.0.1:8791/api/login_status
```

- 改代码后重启：`pkill -9 -f "uvicorn"` 再启动（**不要**只 kill 前台进程）
- 首次启动自动建库 `data/xhs_notes.db`（notes + publish_logs 表）

## 5. 小红书新号登录（换新号演示的关键步骤）

> 安全红线：cookies.json 是登录态，**永不进 git**（.gitignore 已挡）。演示用新号/一次性号，不用业务主号。

1. 在**日常 Chrome** 中打开 xiaohongshu.com，登录演示新号（手机号注册即可）
2. 用豆包 **mac-system-toolkit** 技能导 cookie：
   - 技能目录 `scripts/chrome-cdp/`（`npm install` 后使用）
   - `export_xhs_cookies_cdp.js` 从已登录 Chrome 导出小红书 cookie
   - 写入 `docker/data/cookies.json`（容器 COOKIES_PATH=/app/data/cookies.json）
3. 重启容器使 cookie 生效：
   ```bash
   docker restart xhs-mcp
   # 浏览器访问 http://127.0.0.1:8791 ，界面「登录状态」应显示新号昵称
   ```
4. 二维码登录备选：容器支持登录二维码，但本机实测扫码易被"多端登录"踢——**优先走外部 Chrome CDP 注入**。

## 6. 本机特有、不进 git、需新机重新生成的内容

| 内容 | 位置 | 新机动作 |
|---|---|---|
| cookies.json（登录态） | docker/data/cookies.json | §5 重新导出新号 cookie |
| xhs_notes.db（采集库） | data/xhs_notes.db | 首次启动自动建库；重新采集（POST /api/search） |
| docker/images/ 测试图 | docker/images/ | 一键克隆后自动下载；需重新生成 |
| 发布记录 publish_logs | data/xhs_notes.db 内 | 随库重建 |

## 7. 演示注意事项（重要，避免重蹈本机覆辙）

1. **新号无权重、无案底**：演示可放开采集+评分+一键克隆；**发布演示务必谨慎**：
   - 优先 `visibility=仅自己可见` 演示完整链路（可验证不触发风险）
   - 真发布走「拟人化护栏」：发布前随机 2-5s、冷却 180min±15min、每日≤2、10:00-21:30、风控关键词命中即熔断 24h（已内置于 server.py，无需额外配置）
2. **频率纪律**：本机教训——01:36/01:37 连发即触发平台风控（AI 托管判定），7 天处罚。演示时单次发布、间隔充足。
3. **风控关键词会熔断**：如页面提示验证/频繁/风控，立即停止，不要重试。
4. 采集参数已内置合理随机间隔（2-5s），不要改快。

## 8. 常见坑速查

| 坑 | 解决 |
|---|---|
| Chrome CDP 连不上 | 端口/UUID 每次重启变，**现读** `~/Library/Application Support/Google/Chrome/DevToolsActivePort`，不硬编码 |
| 容器 401 / 无登录态 | cookie 未注入或过期 → 重导 cookie → `docker restart xhs-mcp` |
| Python 3.14 装依赖失败 | 换 3.11-3.13 |
| GitHub https 慢/失败 | 走 SSH（ssh.github.com:443）；https 需代理 |
| 改代码不生效 | `pkill -9 -f "uvicorn"` 后重启（service 层无热重载） |
| Docker daemon 掉线 | `open -a Docker` 等待就绪再 compose |

## 9. 开发调试指南（新环境主要用途）

### 9.1 跑单元测试（评分引擎）
```bash
cd ~/Desktop/codex-zhuke/app
source .venv/bin/activate
pip install pytest coverage
pytest app/test/test_score.py -v        # 期望 20 passed（评分引擎 91% 覆盖）
```
> 注：pyproject.toml 的 coverage 门限 ≥80%；`collect_pipeline.py` 依赖容器（MCP），不纳入单测，走人工冒烟。

### 9.2 联调顺序（从底向上，便于定位问题）
1. **容器层**：curl `localhost:18060/mcp` 有响应 → 容器 OK
2. **登录态**：`/api/login_status` 返回新号昵称 → cookie 注入 OK
3. **采集**：`POST /api/search {keyword:"翡翠"}` 落库 → 采集+评分 OK
4. **克隆**：`POST /api/clone {feed_id}` 下载图片 → 一键克隆 OK
5. **发布**：仅自己可见 → 护栏生效（日志可见 human_delay/冷却）→ 发布链路 OK

### 9.3 前端调试
- 前端为原生单文件：`app/web/index.html`（4-Tab，含确认框+熔断提示+拟人化档位条）
- 修改后直接刷新 `http://127.0.0.1:8791` 即可（StaticFiles 挂载，无构建步骤）
- 后端改动后必须 `pkill -9 -f "uvicorn"` 重启才生效

### 9.4 调试期安全底线（比功能更重要的纪律）
1. 发布演示**只用演示新号/一次性号**；业务主号永不用于调试
2. 优先 `visibility=仅自己可见`；真发布单次、间隔充足（本机 01:36/01:37 连发触发 AI 托管判定的教训）
3. 风控关键词（验证/频繁/风控/拦截/操作过快）命中 → 熔断 24h，**不要重试**
4. 采集参数内置随机间隔（2-5s），调试勿改快
